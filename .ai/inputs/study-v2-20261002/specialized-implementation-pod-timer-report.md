WHERE I DEPARTED FROM YOUR SKETCH (please check these)
1. Admission requires a recorded observed self-stop (`stop_confirmation` in the shutdown config). The timer's acknowledgement proves a deadline is enforced, not that RunPod acts on a stop a pod asks for itself, and the docs do not say what the pod-scoped key may do. The validation's first step produces it with no lease: a pod with a ten-minute cap, laptop off, seen to stop. If you think this gate is too strict, it is one check to remove.
2. `RUNPOD_API_KEY` inside a pod is RunPod's own pod-scoped key, so the provider's read key needs another name there. New config key `key_env` (e.g. `RUNPOD_READ_API_KEY`). Without this, admission in the pod would read with the wrong key.
3. "Latest valid record governs" became "most recently issued valid authority governs", the cap included. Otherwise a pod stopped at its deadline could never be used again: on restart the old lease is past, so the timer stops it at once. The operator restarts with a new cap, which outranks old leases.
4. The supervisor is not PID 1. The start command's shell stays as the first process and, if the supervisor ever exits or the script cannot be unpacked, asks RunPod to stop the pod itself. This avoids depending on whether RunPod restarts a container whose command exits (undocumented).
5. As a backup the watchdog's stop time is the END of the reservation, not minus its lateness. Otherwise it would stop the pod before the timer, mid-lease.
6. The deadline is enforced from memory by a thread that never touches the mount; a hung network volume silences the heartbeat but cannot block the stop.

DESIGN
- `pod_timer/pod_timer.py`: stdlib, Python 3.8+, self-contained. Modes: `supervise -- /start.sh`, `run`, `status`.
- Start command (generated by `python -m experiments.durability pod-timer-settings`): the script travels gzip+base64 in env (`POD_TIMER_B64_00`, 10,620 chars; `--chunk-chars` splits it), is unpacked to the container disk, checked against a SHA-256 written in the command, and run as `python3 -I ... supervise -- /start.sh`. On any failure: loop of `runpodctl pod stop`, `runpodctl stop pod`, then curl to the REST stop.
- State on the mount (`/workspace/.pod-timer`): `leases/`, `voids/`, `acks/`, `heartbeat.json` (every 2 s), `stop-attempts.jsonl`, `starts.jsonl`, `backups/`.
- Arm (`shutdown_timer.PodTimer.arm`): state folder confirmed persistent by RunPod; stop confirmation recorded; heartbeat ≤ 15 s old, this pod, supervised, not stopping, able to ask for a stop; lease record written create-only with stop = end of reservation − lateness; within 30 s the timer's acknowledgement AND a later heartbeat naming this lease and stop time; else void and refuse.
- At the deadline: `runpodctl pod stop`, `runpodctl stop pod`, REST stop, GraphQL podStop, each recorded, repeated every 15 s while still alive. Never terminate/delete/reset/restart.
- `LayeredShutdown`: timer required; backup attempted with a bounded wait (120 s + 30 s), outcome written to `backups/<lease>.json` and returned, never required. A renewal whose backup arm fails withdraws every earlier backup arm, so the watchdog cannot stop a renewed pod.
- Lateness: recommended `lateness_seconds = 120` and `shutdown_delay_seconds >= 120` (RunPod's stop latency, unmeasured). The existing lateness rule in admission is unchanged; no other admission input loosened.
- Stage B: the timer adds no time inside sessions; arming is in admission. Decision 4 stays deferred.
- New CLI: `pod-timer-settings`, `check-timer`. Config: `"shutdown": {"kind": "pod-timer", "state_dir", "lateness_seconds", "stop_confirmation", "backup": {"kind": "github-actions-watchdog", "repository"}}`.

REJECTED
- A stop time at creation (`stopAfter`/`terminateAfter`): undocumented, cannot be confirmed.
- Script on the network volume: empty at first boot.
- Custom image with the timer baked in: needs a registry and a build; a possible later hardening.
- A grace period when the deadline is past at start: a crash loop would bill forever.
- Single-threaded timer: a hung mount would block the stop.

KEYS
- Pod-scoped key (`RUNPOD_API_KEY` in the pod): put there by RunPod; used by the timer to stop its own pod. Scope undocumented. The worker can read it; we cannot prevent that.
- Read Only account key (`RUNPOD_READ_API_KEY`, via a RunPod secret): admission's reads.
- Backup token: unchanged.
- The user's stop-capable key: GitHub Actions secret only, never on the pod.

DEPLOYMENT STEPS FOR YOU
1. Generate settings shortly before creating the pod (the cap counts from then): `python -m experiments.durability pod-timer-settings --state-dir /workspace/.pod-timer --cap-minutes N --out settings.json`.
2. Cap-only check first. Only after it can `stop_confirmation` be written and admission succeed.
3. Provider config: add `key_env` and the `pod-timer` shutdown section; policy `shutdown_delay_seconds >= 120`.
4. Redeploy watchdog.py + watchdog.yml (new pin) together with the pod's entry in pods.json, if you want the backup.

STEPS FOR THE USER
1. Create a Read Only RunPod key; store it and the backup token as RunPod secrets.
2. Create the network volume, then the pod on it: mount at /workspace; every variable from settings.json; `RUNPOD_READ_API_KEY={{ RUNPOD_SECRET_... }}` and the backup token likewise; the start command from settings.json. Do not set RUNPOD_API_KEY.
3. Within minutes: `cat /workspace/.pod-timer/heartbeat.json` must exist, be seconds old, and say supervised true. No heartbeat: stop the pod by hand.
4. To reuse a stopped pod: regenerate settings, replace the two POD_TIMER_CAP_* values, start it.

WEAKEST ASSUMPTION
That RunPod acts on a stop requested from inside the pod with what it preinstalls there.
Counterexample: the image's runpodctl is old or unconfigured and the pod-scoped key is rejected by REST and GraphQL; every method fails, the timer loops, and the pod runs until GitHub's next scan (hours) or the balance hits zero.
Settling check: the cap-only pod. Ten minutes of GPU, laptop disconnected; look from outside for EXITED at the cap, and read stop-attempts.jsonl afterwards for which method worked and how long it took. Admission stays closed until that is recorded.

UNCOVERED BY ANYTHING OF OURS
A pod whose container never starts (image pull fails, start command never runs): no timer, no lease, no backup arm. The operator's heartbeat check after creation is the only guard, plus RunPod's stop at zero balance. If `stopAfter` at creation turns out to be enforced, it would close this.
