## 12. Unresolved concerns (not defects)

- C1. The detached orchestrate child of a Llama host holds the token in its environment from launch to the gated step (E 10-20 min after bootstrap; bounded by the pod's cap if ssh hangs, since `tool()` has no timeout). Readable by the same macOS user through `ps -E`. The family-probe design; consistent with C13 ("the HF token in the Mac environment at each Llama launch") and the 7 Oct decision ("reaches a pod only through the ssh-stdin step").
- C2. `StrictHostKeyChecking=accept-new` pins the pod's host key at the first ssh (wait-ssh); if RunPod changes the pod's public ip:port before the gated step, the new address's key is accepted without a check at that moment (a one-time MITM window on the connection that carries the token). Same in the family-probe and the stage-1 kit. A pinned RunPod-provided key is not available (I).
- C3. Mac-side records are scanned for secrets at backup time (and by the tests with a fake token), not when written. Pod-side records are scanned by the finisher. Acceptable; stated.
- C4. The whoami request sends whatever is in HF_TOKEN before any shape check; a wrong value pasted in (another service's key) would go to huggingface.co as a Bearer. A `fullmatch` on the hf pattern before the first request would refuse it at $0. Hardening only.
- C5. Proxy and CA environment variables (HTTPS_PROXY, SSL_CERT_FILE) are honored by urllib and huggingface_hub; the kit does not pin or refuse them. The Mac is the user's; out of this kit's scope; stated.
- C6. `TypeError` added to the unreadable-reply except (launch.py:100) widens the warn path by a shape the original would have crashed on. Harmless; noted for completeness.
